# A3.2–A3.6 — Identity, Localization, Audit, and Offline Contracts

**Repository:** `akefadaka-git/ekhc-digital-platform`  
**Branch:** `a3/owner-approved-identity-security-foundation`  
**Implementation status:** Contract-level implementation; exact-head CI and A4 review required  
**Data policy:** Synthetic fixtures only; no institutional records or live credentials

## A3.2 — Authentication and session security design

Implemented non-persistent contracts for a future authentication provider and browser-session adapter:

- `AuthenticationProvider` is an explicit verifier boundary. No password store, identity provider, OAuth/OIDC issuer, credential exchange, or account-recovery provider is selected or implemented.
- `SessionObservation` models only trusted server-side facts: typed account reference, issue time, last activity, absolute expiry, authentication state, and revocation state.
- `evaluate_session` uses an injected timezone-aware clock observation and fails closed for revoked, unauthenticated, future-dated, idle-expired, or absolutely expired sessions.
- `SessionPolicy` requires idle and absolute lifetimes and mandatory session rotation after authentication and security-boundary changes.
- `SessionCookiePolicy` requires Secure, HttpOnly, host-only cookies and SameSite Strict/Lax. The current Django project does not enable a session or authentication backend; these are requirements for a future adapter, not active session controls.
- Existing HTTPS/HSTS production configuration checks remain separate; no proxy topology or SSO domain assumptions were introduced.

**Not implemented:** credential verification, login/logout endpoints, MFA, session issuance/storage, cookie middleware, refresh tokens, password reset, recovery, rate limiting, provider selection, or account linking. These require a selected and reviewed identity provider, account lifecycle owner, session persistence/security architecture, and deployment boundary. No user-controlled timestamps are accepted by the evaluation function.

## A3.3 — Person/account identity boundary

- Person and account identifiers remain distinct immutable opaque types.
- A link can exist only as an explicitly constructed typed `IdentityLink`; matching string values do not infer identity.
- Negative tests cover cross-type substitution, untyped values, immutability, malformed references, and absence of inferred links.
- No Django models, persistence, verification, membership state, duplicate resolution, roles, offices, or institutional authority are introduced.

## A3.4 — Amharic-first localization and calendar boundary

- Existing request-scoped language negotiation remains Amharic-first (`am`) with explicitly supported English (`en`) and fallback behavior.
- Added NFC Unicode normalization that preserves script, whitespace, and exact terminology semantics; it does not translate, transliterate, or rewrite institutional terms.
- Added validated Ethiopian calendar date values and an explicit adapter protocol for conversion to/from Gregorian dates.
- Ethiopian leap-year/Pagume validation is covered by synthetic test vectors.
- Gregorian preference returns the Gregorian date without invoking the Ethiopian adapter.

**Not implemented:** a production conversion library, account-level language/calendar preferences, translation catalogues, institutional terminology translations, UI, or persistence. Calendar conversion must be supplied and independently validated by a chosen authoritative adapter before production use.

## A3.5 — Audit and records foundation

- Added immutable, minimal audit event values: event UUID, actor account reference (optional), action, resource type/reference, timezone-aware event time, correlation UUID, and outcome.
- Added a write-only `AppendOnlyAuditSink` protocol. It exposes append only; no update/delete/query/retention behavior is specified.
- Added document metadata and immutable version value objects with MIME type, version, size, SHA-256 integrity reference, and timezone-aware timestamps.
- Added a typed document access request, deny-all default policy, and metadata-store protocol. No role/office mapping or file-byte storage is provided.
- Tests cover event immutability, typed actors, normalized event identifiers, metadata/version validation, access default-denial, timestamp awareness, and generated event identifiers.

**Not implemented:** durable storage, cryptographic integrity chaining, access control, retention/disposal, legal hold, backup/recovery, document storage, or records classification. These require approved institutional records policy and a selected storage/security design.

## A3.6 — Offline synchronization foundation

- Added a metadata-only sync envelope with UUID idempotency key, opaque aggregate/device references, base version, SHA-256 payload digest, and timezone-aware client creation time.
- Added a pure evaluator for idempotent replay, version match, and version conflict. It does not apply mutations or treat client time as authoritative.
- Added explicit queue/in-flight/acknowledged/conflict/retryable/permanent-failure state transition rules.
- Added a ciphertext-only local record contract and an `EncryptedLocalStore` protocol. The contract carries ciphertext and opaque key/suite references only.

**Not implemented:** an encrypted database/filesystem adapter, cryptographic implementation, key provisioning/rotation/recovery, durable outbox, server sync API, transactional apply, multi-device conflict resolution, background scheduling, or real data. A reviewed cryptographic/key-management provider and data minimization/retention decisions are required before production storage.

## A3.4–A3.6 implementation detail

- Ethiopian calendar conversion is implemented using ICU-aligned Amete Mihret Julian-day arithmetic, with new-year, Pagume 5/6, and round-trip regression vectors. No external Python calendar package is required.
- Audit persistence is specified for PostgreSQL with append-only application privileges, hash-chain verification, and encrypted object storage for document bytes. Retention, purge, and legal-hold durations remain unset pending institutional approval.
- Synchronization accepts ciphertext envelopes only. AES-256-GCM/KMS ports enforce per-payload DEKs, 96-bit nonces, 128-bit tags, authenticated-data binding, and transient mutable-key zeroization. The PostgreSQL unit-of-work port atomically coordinates aggregate version, idempotency receipt, audit event, and metadata-only outbox record.
- Provider ports are not production adapters. No live database, KMS, object store, or device key is configured; test-only reversible ciphers are never production eligible.
