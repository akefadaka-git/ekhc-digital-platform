## 1. Purpose and verification rules

A4 independently verifies that the A3.2–A3.6 implementation satisfies its approved technical contracts and that no unapproved institutional authority or retention policy has been introduced.

A4 is not a repetition of implementation. The verifier must inspect the exact source SHA, test evidence, dependency state, and adapter boundaries. Every result is labelled PASS, FAIL, PARTIAL, MISSING, UNRESOLVED, or NOT RUN. A4 may not be marked closed while a required provider, storage adapter, cryptographic implementation, policy source, or recovery test is missing.

Use synthetic data only. Do not provision production credentials, import institutional records, enable live delivery, create live KMS keys, or deploy services during this verification plan.

## 3. A4.2 — Authentication and session security

### Static and unit verification
- Confirm no credential provider, password store, recovery endpoint, or live session backend is enabled by default.
- Confirm authorization remains deny-by-default and no role, office, hierarchy, or membership grants exist.
- Verify session evaluation rejects revoked, unauthenticated, future-dated, idle-expired, and absolutely expired observations.
- Verify one injected trusted-time observation is used for each evaluation.
- Verify Secure, HttpOnly, host-only cookies and SameSite Strict/Lax policy constraints.
- Verify session rotation requirements cannot be disabled by configuration.

### Provider integration — blocked until selected
- Identify and review the actual identity provider and account lifecycle owner.
- Test login/logout, session issuance, rotation, revocation, CSRF, fixation, replay, MFA where required, recovery, rate limiting, and concurrent sessions.
- Verify session persistence and key/token protection under the selected deployment boundary.

**Exit:** no production authentication claim until the provider and integration tests are independently reviewed.

## 5. A4.4 — Ethiopian calendar conversion

### Source and algorithm conformance
- Confirm the implementation follows ICU Ethiopic Amete Mihret / CECalendar arithmetic: Julian-day epoch offset 1,723,856, 1,461-day four-year cycles, twelve 30-day months, and five/six-day Pagume.
- Independently cross-check the reference vectors against a pinned ICU implementation, not only against the adapter's inverse function.
- Verify new-year transitions, Pagume 5/6 boundaries, leap-year cycle boundaries, Gregorian leap-year interactions, and round trips over a broad generated date range.
- Verify invalid dates and dates before the supported epoch fail explicitly.

### Explicit limits
- Current adapter supports positive Amete Mihret years only.
- Amete Alem, historical calendar reforms, Ethiopian time conventions, time-of-day conversion, holidays, and localized month labels are outside this implementation.
- Do not add unverified date or terminology libraries without provenance, licence, maintenance, and independent-vector review.

**Exit:** PASS only after independent ICU conformance vectors pass. Otherwise mark PARTIAL.

## 6. A4.5 — Durable audit and records storage

### Design verification
- Confirm PostgreSQL is the selected transactional system-of-record design for audit events, document metadata/version manifests, idempotency receipts, and outbox metadata.
- Confirm document bytes are stored as ciphertext in a private versioned object-store adapter.
- Confirm audit events are canonicalized and chained with sequence, predecessor digest, and event digest.
- Confirm the application audit database identity is INSERT/SELECT only; no application UPDATE/DELETE privileges.
- Confirm business mutation, audit append, and outbox insert share the same database transaction.
- Confirm object upload is staged, checksum-verified, and promoted to an immutable version before metadata is finalized.

### Required integration evidence — not yet available
- PostgreSQL integration tests for transaction isolation, row-lock concurrency, unique sequence/idempotency constraints, and rollback after audit insert failure.
- Privilege tests proving application credentials cannot update/delete audit events or prior document versions.
- Chain tamper, deletion, reorder, gap, and externally anchored backup verification.
- Object-store checksum mismatch, interrupted upload, version collision, and orphan reconciliation tests.
- Encrypted backup, restore, audit-chain continuity, object availability, and key-recovery exercises.

### Retention policy boundary
Retention duration, archival period, legal-hold period, and disposal rules remain UNRESOLVED. No retention duration is inferred from this plan. Do not enable purge jobs, deletion APIs, or object lifecycle expiry until an authoritative institutional policy is supplied and approved.

**Exit:** PARTIAL until PostgreSQL and object-store adapters, privilege tests, backup/restore evidence, and authoritative retention requirements are available.

## 7. A4.6 — Cryptography and key management

### Contract verification
- Confirm AES-256-GCM is the required production suite, with 256-bit per-object/version DEKs, 96-bit nonces, and 128-bit tags.
- Confirm AAD binds object reference, version, media type/schema version, and sync operation identity.
- Confirm wrapped DEKs and KMS key references are stored; plaintext keys are not persisted or logged.
- Confirm transient mutable DEK buffers are zeroized on both encryption and decryption success/failure paths.
- Confirm key rotation re-wraps DEKs and compromise recovery requires re-encryption/revocation.

### Required provider integration — not yet available
- Select and independently review a managed KMS/HSM provider and key-custody model.
- Verify NIST AES-GCM known-answer vectors, invalid-tag rejection, AAD substitution rejection, nonce uniqueness, and ciphertext tamper rejection.
- Verify KMS generate/unwrap/rewrap, key-version changes, rotation, revocation, outage, recovery, backup, and restore.
- Confirm key material is absent from logs, crash reports, test artifacts, and repository history.
- The reversible cipher used by tests is test-only and must never be treated as a production implementation.

**Exit:** PARTIAL until a real AES-GCM library and KMS/HSM adapter pass independent conformance tests.

## 8. A4.7 — Transactional synchronization

### Existing synthetic tests
- Verify idempotent replay returns the prior receipt without reapplying a mutation.
- Verify version mismatch records conflict and does not overwrite aggregate state.
- Verify aggregate mutation, receipt, audit event, and outbox are atomic.
- Inject audit-insert and outbox-insert failures and prove complete rollback.
- Verify one trusted timestamp observation is reused for the transaction.
- Verify the outbox stores metadata only and contains no ciphertext/plaintext payload.

### Required database and restart integration
- Run concurrent duplicate requests against PostgreSQL and prove only one mutation is committed.
- Run concurrent version updates and prove compare-and-swap/row locking prevents lost updates.
- Test process crash before commit, after commit before response, after outbox enqueue, and during delivery.
- Verify restart replay, at-least-once delivery, consumer deduplication, acknowledgement, bounded retry, dead-letter/quarantine, and explicit conflict resolution.
- Verify encrypted local queue restart/recovery and device-key loss/re-enrollment using Android Keystore/StrongBox integration tests.

**Exit:** PARTIAL until the real PostgreSQL unit-of-work and device/offline adapters pass integration and fault-injection tests.
