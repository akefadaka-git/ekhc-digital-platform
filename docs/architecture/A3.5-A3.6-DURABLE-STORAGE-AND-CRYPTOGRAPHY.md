# A3.5 / A3.6 — Durable Storage and Cryptographic Sync Architecture Decision

**Status:** Approved technical design for A3 implementation; production activation remains gated by infrastructure and security verification.  
**Scope:** Generic application records only. No institutional retention period, membership rule, office/role, or authority mapping is defined.

## A3.5 — Durable audit and records storage

### Decision

Use PostgreSQL as the transactional system of record for audit events, document metadata, version manifests, and synchronization receipts. Keep document bytes outside the relational database in a private, versioned object-storage adapter. The object store must support immutable object versions, conditional writes, integrity checks, server-side encryption, and independent backup/recovery.

### Audit event durability and integrity

- Append audit events in the same database transaction as the business operation they describe (transactional audit).
- Persist a canonical, versioned event representation with event UUID, server-observed UTC timestamp, actor reference where available, action, resource reference, outcome, correlation ID, schema version, and payload digest.
- Exclude request bodies, credentials, session tokens, personal-data payloads, and arbitrary free-form metadata.
- Use per-stream hash chaining (previous digest + canonical event digest) and a unique sequence constraint to make alteration, deletion, reordering, or gaps detectable. The chain head is advanced under a database row lock in the same transaction as the event insert.
- Application database credentials receive INSERT/SELECT only on the audit relation; no UPDATE/DELETE. A separate tightly controlled migration/administration identity owns schema changes. External immutable backup copies provide a separate trust boundary.
- An audit write failure aborts the associated business transaction. No "best effort" audit writes.

### Records and document storage

- PostgreSQL stores document reference, media type, version number, byte size, SHA-256 checksum, opaque object key, encryption envelope metadata, created/updated timestamps, and actor reference where available.
- Object storage holds ciphertext only. The database stores wrapped data-key reference and algorithm/version identifiers, never plaintext data keys.
- New versions are append-only; current version is a pointer/manifest update under optimistic version check. Deletion is a separate, explicit lifecycle operation and must not be inferred from an ordinary metadata update.
- Access policy is an injected server-side policy port with deny-all default. No group, office, or institutional role semantics are specified here.
- Object upload uses a staged object key, checksum verification, and a metadata transaction. Orphaned staged objects are reconciled by an operational job only after a reviewed orphan policy; no automatic destructive cleanup is configured.

### Retention and recovery

No retention duration, purge schedule, legal-hold period, or disposal rule is invented. Until the institution approves them, retention is indefinite by default at the application layer, deletion APIs and purge jobs remain disabled, and storage lifecycle expiration is prohibited. This is a technical hold, not a claim that indefinite retention is the final institutional policy.

Backups must be encrypted, access-controlled, independently monitored, and restore-tested. Restore procedures must verify audit hash-chain continuity and object checksum/key availability before service is declared recovered.

## A3.6 — Cryptography and key management

### Decision

Use envelope encryption for local/offline records and document objects:

- AES-256-GCM authenticated encryption for payload confidentiality and integrity.
- A fresh cryptographically random 256-bit data-encryption key (DEK) per object/version; never reuse a nonce with the same DEK.
- A 96-bit unique nonce and 128-bit authentication tag; persist nonce, tag/ciphertext, algorithm suite/version, wrapped DEK, KMS key reference/version, and authenticated-encryption associated data (AAD) binding opaque object reference, version, media type, and schema version.
- Wrap each DEK using an external KMS/HSM-managed key-encryption key (KEK). Plaintext DEKs exist only transiently in process memory and are never persisted or logged.
- Key rotation re-wraps DEKs under the new KEK without re-encrypting payload bytes where the KMS policy permits. Compromise response requires re-encryption and revocation. Recovery requires tested KMS backup/escrow and dual-control procedures.
- Production must use a maintained cryptographic library and a managed KMS/HSM adapter. No custom cipher, local hard-coded key, environment-stored master key, or software-only key vault is permitted.

No KMS vendor, credentials, key hierarchy, rotation cadence, escrow authority, or recovery custodians are selected here. The ports are vendor-neutral; production encryption remains disabled until a provider and operational key-custody model are independently approved and tested.

## A3.6 — Transactional synchronization

### Decision

Use PostgreSQL transactions and a transactional outbox for synchronization. Each accepted client operation must atomically:

1. Claim a unique idempotency key scoped to the authenticated account/device context.
2. Lock or compare-and-swap the target aggregate version.
3. Validate the base version and apply the domain mutation.
4. Append the audit event and new aggregate version.
5. Insert an outbox event for downstream delivery.
6. Commit once.

Any failure before commit rolls back all six effects. Replays return the recorded outcome and do not repeat the mutation. Version mismatches produce an explicit conflict record and never overwrite server state. Outbox delivery is at-least-once; consumers deduplicate by event UUID. Acknowledgement is persisted only after downstream acceptance. Retry uses bounded exponential backoff with jitter; permanent failure is quarantined for operator review, not silently discarded.

### Local offline queue

- Store encrypted envelopes only; device keys are held in Android Keystore/StrongBox where supported and hardware-backed status is recorded, not assumed.
- Keep plaintext payloads out of logs, backups, crash reports, and notification previews.
- Local queue entries have stable UUID idempotency keys and explicit queued/in-flight/acknowledged/conflict/retryable/permanent states.
- Recovery after restart replays queued/in-flight operations idempotently. A conflict requires explicit reconciliation before requeue.
- Device loss triggers server-side device/session revocation and KMS/device-key recovery or re-enrollment; no bypass recovery path is allowed.

## Adapter ports to implement

- `AuditEventRepository` — transactional append and chain-head verification.
- `DocumentMetadataRepository` — append versions and compare-and-swap current version.
- `EncryptedObjectStore` — staged ciphertext put/get/verify, no plaintext interface.
- `KeyEncryptionProvider` — wrap/unwrap DEKs; provider owns KEK material.
- `PayloadCipher` — AES-256-GCM encrypt/decrypt with explicit nonce and AAD.
- `SyncUnitOfWork` — one database transaction spanning idempotency, aggregate mutation, audit append, and outbox insertion.
- `SyncRepository` — idempotency receipt, aggregate version, and outbox operations.

The code branch will define these contracts and deterministic fake-adapter tests. No live database, object store, KMS, device keystore, or institutional records are configured. A4 must verify atomic rollback, duplicate/replay safety, tamper detection, encryption metadata/AAD binding, key rotation behavior, and backup/restore before production activation.

## A3.4 — Ethiopian calendar provider validation

The selected arithmetic reference is Unicode ICU's Ethiopic Amete Mihret implementation: ICU's `EthiopicCalendar` delegates to `CECalendar.ceToJD` / `jdToCE`, with epoch offset 1,723,856, 1,461-day four-year cycles, 12 × 30-day months, and a five/six-day Pagume. The Python adapter mirrors that documented arithmetic and is checked against independent Gregorian reference vectors and round trips.

Third-party Python candidates were reviewed but not selected as runtime dependencies: the surfaced `ethiocalendar` package labels itself beta and its current release page reports no build provenance; the newer `ethiopian-calendar` package is a single-maintainer new release. A small, auditable adapter avoids adding an unverified dependency. ICU remains the reference algorithm; deployment should pin and test the ICU reference version used for conformance.

**Limits:** positive Amete Mihret dates only; no Amete Alem era, historical date reforms, time-of-day conversion, Ethiopian time convention, holiday computation, or localized month names. Calendar arithmetic is not a substitute for institution-approved display terminology.

## Verification gates

- Unit tests compare conversion vectors, leap Pagume boundaries, and round trips.
- CI runs the full Django suite, Ruff, and pip-audit.
- A4 separately verifies database isolation/rollback, append-only privileges, chain integrity, object-store consistency, key-provider conformance, cryptographic tamper rejection, and crash/restart replay.
- No merge, deployment, key provisioning, data migration, retention configuration, or publication is authorized by this ADR.
