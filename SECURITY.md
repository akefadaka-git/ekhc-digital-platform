# Security Policy

## Reporting a vulnerability

Please do not report suspected vulnerabilities in public GitHub issues, discussions, pull requests, or commits. Do not publish credentials, exploit payloads, personal data, or details about private environments.

1. If GitHub's **private vulnerability reporting** feature is enabled for this repository, use the repository's Security tab and submit a private report.
2. This repository's feature availability and notification routing have not yet been independently verified. If private reporting is unavailable, use an already-known, authenticated private contact channel with the Repository Owner. Do not guess or scrape an email address or send sensitive details through a public channel.
3. Include the affected component, ecosystem, version/range, advisory identifier or source, dependency path if known, impact, reproduction summary, and a safe reply route. A proof-of-concept is not required for initial intake.
4. Allow coordinated disclosure. Do not publicly disclose exploit details before an agreed disclosure date unless required by applicable law or an immediate safety concern.

## Response expectations

The repository's vulnerability intake and triage process defines acknowledgement, triage, containment, remediation targets, escalation, and exception governance:

- [Vulnerability Advisory and Exception Governance](docs/security/VULNERABILITY-ADVISORY-AND-EXCEPTION-GOVERNANCE.md)

The response targets in that policy are process objectives, not a claim of staffed 24/7 coverage or a guarantee that a report has been received. The repository must verify its private intake configuration and responder coverage before claiming operational readiness.

## Supported versions

The repository currently has no published production release support matrix. Report the exact branch, commit, package versions, and environment believed to be affected. Do not assume that a branch name alone establishes production support.
